## Complier-specific interpretation

The recommended architecture remains the user's current one: native tool-call attempt → CEL translation → abstract CSP event → whole-composition authorization/refusal → original harness execution/authentication. There is no new polling path or uncontrollable-event partition being imposed by this research.

Use a single authoritative contract-instance state across relevant harness sessions/subagents, not independently mutable per-session state when sessions share a composition. Refusal is state-preserving; if modeled through CSP interleaving, retain that behavior. Adapter requests should include actual available provenance/call identifiers, but must not invent missing IDs. Whole-composition priority/order belongs in the guard/contract semantics rather than whichever parallel hook happens to finish first.

The Exa recommendation to distinguish attempt/dispatch/success is a modeling choice for the user, not a request to replace the current model. If events mean accepted attempts, commit at that boundary. If they mean successful execution, pre-hook authorization needs reservation/correlation rather than preemptive success advancement. A tool may partially perform an effect then fail; releasing a reservation cannot undo that effect. Missing post-hooks require an explicit unknown-outcome/recovery policy.

A useful portable core can normalize provenance, exact arguments, policy revision, decision IDs and feedback. It must still emit the specific harness's actual deny schema. Treat a daemon outage as a native refusal where supported; configure the daemon-client deadline shorter than the harness hook timeout so the adapter can return a real denial before the host decides timeout behavior. That improves a reachable adapter's outage behavior; it does not erase host timeout fail-open behavior, skipped config or missing adapter processes.
